# DOL007 — Possible N+1: attribute access inside for-loop

**Default severity:** warning · **Applicability:** unsafe · **Category:** queryset

Detects `for x in <queryset>:` followed by an `x.<attr>` access in the loop body (first 15 lines; `id`, `pk`, `save` and underscore-prefixed attributes are ignored, one finding per loop). If `<attr>` is a `ForeignKey` / `OneToOneField`, each iteration triggers a separate query — the classic N+1: one query for the loop plus one per row. `select_related()` (SQL join) or `prefetch_related()` (batched second query) collapse that into constant query count.

The rule is line-oriented and has no type information, so it cannot tell an FK from a plain field — which is why it is `unsafe` and ships no QuickFix. It also does not track whether the queryset already has `select_related` coverage; the CLI's schema-aware [`nplusone` analyzer](nplusone.md) does. After fixing (or for scalar fields), suppress the finding.

## Which loops are in scope

The iterable has to look like a queryset: a chain rooted at `<Model>.objects.…`, or one beginning with a queryset-producing method (`all`, `filter`, `exclude`, `annotate`, `distinct`, `order_by`, `values`, `values_list`, `reverse`, `none`, `iterator`, `only`, `defer`, `using`). The CLI's `nplusone` analyzer tests a loop source the same way, but the two do not report the same loops: the analyzer works from an AST and follows what a helper returns, so a helper call that yields a queryset — `recent()`, `self.get_queryset()` — is in scope there and is not reported here.

Loops over `range(10)`, `os.listdir(path)` or `apps.get_models()` are not reported: they iterate ranges, lists or model *classes*, where an attribute read is an in-memory lookup and `select_related()` has nothing to act on. A helper call such as `auditory_models()` is skipped for a different reason — the call name alone says nothing about what comes back, and finding out means following the helper's return, which needs the AST this rule does not have. The cost is the false negative above: a helper that does yield a queryset is missed here.

A loop over a bare name (`for user in users:`) **is** reported: it names no call, so it is evidence neither way, and `users = User.objects.all()` is the common idiom — which the `nplusone` analyzer reports too, resolving the name through an AST tracker that binds it to the queryset assigned to it. The divergence is narrower than the loop head suggests: only a name that tracker cannot bind to a queryset — a function parameter, an import, or a name assigned anything else, a helper call included even when the helper returns a queryset — is reported here and not there.

## Bad

```python
for post in Post.objects.all():
    print(post.author.name)   # one extra query per post
```

## Good

```python
for post in Post.objects.select_related("author"):
    print(post.author.name)   # single joined query
```

## Suppress

```python
# django-orm-lens-disable-next-line DOL007
```

Or per-workspace in `.vscode/settings.json`: `{"djangoOrmLens.rules": {"DOL007": "off"}}`.
